# Native UI capture coverage

Audit anchor: `58a7244e2b3d4d0f43e0a80517d8ffdb462ad5b4` (2026-10-18). This is a read-only source audit. No servers, worlds, builds, tests or live API calls were started. Runtime navigation and rendering are unverified by this audit; committed test scripts describe intended checks, not proof that every native panel/tab/layer was exercised.

**The capture interfaces do not cover every native information panel and control.** The selected-image API exposes a native world viewport and exactly two native information panels: own-company finances and the town directory. Town directories have explicit sorting and row selection; name filtering is absent. The minimap's seven layers have a static path through the legacy image-bound native GUI, but no selected minimap request. The current capture MCP adapter exposes neither that legacy image/control path nor `ui.apply`, so legacy HTTP reachability does not establish MCP coverage.

A text query is not capture coverage. A viewport image is not a minimap layer. A composed screenshot can contain an already-open window but does not prove that a caller can open it, select its tabs, change its filters or navigate every state. A native-input allowlist is necessary for a GUI path, but is not a generic window opener or runtime acceptance result.

The inventory accounts for all 110 `WindowClass` names: `None` and `MainWindow` alias one value; `Invalid` is a sentinel; 108 distinct usable values remain. Classes are not panel counts: vehicle-list classes pack context/group views, `CompanyLeague` includes script tables, `GameOptions` has five window-number variants, and several construction classes pack transport-specific pickers. The appendix retains those distinctions.

## How to read the coverage matrix

| Mark | Meaning |
| --- | --- |
| **D** | Direct selected noninteractive native image, with the stated finite presentation controls. |
| **G** | Concrete legacy HTTP screenshot/control/`ui.apply` path exists in source; current capture MCP does not expose it. Runtime unverified. |
| **P** | Partial presentation, ownership, input or event-context restrictions. This can qualify D or G. |
| **M** | Missing from the stated public surface, or no supported path to the relevant state was established. |
| **N** | Alias/sentinel, control-only or outside ordinary company gameplay; still inventoried rather than omitted. |
| **C** | Existing native content/context is required; this does not establish an unconditional opener. |

Every G row requires the common legacy protocol described below, plus its native entry path. Unless a row explicitly states D, it is M on the selected-image and current capture-MCP observation surfaces. A visible but unsupported child window is classified as passive/partial, not fully navigable. Editor/debug/startup and ordinary-play information are accounted for separately.

## Concrete legacy information-window family matrix

Common public chain for all GUI rows: authenticate visual actor → `POST /v1/view/images {}` → authenticated `GET /v1/images/{id}` → inspect pixels → `POST /v1/actions` with `ui.apply`, exact owned interaction `image_id`, coordinates and click/drag → wait receipt → acquire/download/inspect fresh screenshot for each next step. The current capture MCP adapter cannot perform this chain because it lacks legacy screenshots/controls and rejects `ui.apply`. Read-only screenshot/view controls also work for text mode; `ui.apply` is visual-only. [service.py](../backend/service.py#L481), [service.py](../backend/service.py#L772), [renderer.py](../backend/renderer.py#L927), [capture_tools.py](../backend/capture_tools.py#L274).

Toolbar dispatch is concrete: native `MainToolbarWindow::OnClick` calls `_toolbar_button_procs[widget]`, while `OnDropdownSelect` calls `_menu_clicked_procs[widget]`, with integration result restrictions before dispatch. [toolbar_gui.cpp](../src/toolbar_gui.cpp#L2002), [toolbar_gui.cpp](../src/toolbar_gui.cpp#L2069). Allowed toolbar widgets cover the entries listed below; native dropdowns are permitted only with captured allowed parent/provenance. [renderer_input.cpp](../src/integration/renderer_input.cpp#L292), [renderer_input.cpp](../src/integration/renderer_input.cpp#L453). Native disabled widgets are rejected before dispatch. ## Prioritized gaps and minimal design suggestions

These are suggestions for separate design review, not implemented extensions or authority to change code.

1. **Expose existing HTTP capture controls to MCP if broad native-GUI access is required.** The server already has interaction screenshots, immutable PNG download, finite view controls and image-bound UI input, but the seven-tool adapter omits them and rejects `ui.apply`. Thin optional wrappers that reuse those existing identities, leases and request ledger would make existing server functionality available; a second UI state manager or action ledger is unnecessary. Return actual image content and preserve receipt recovery and proof expiry.
2. **Add an explicit selected minimap presentation.** Extend the existing finite native-info family only after reviewing native drawing/state restoration: caller-chosen layer (all seven), bounded center/zoom/dimensions, labels and native legend selections. The caller chooses cargo/company/industry visibility. Do not substitute a world viewport or choose a commercially useful layer/site on the caller's behalf.
3. **Extend operational panel capture one native family at a time.** Station cargo/routing/ratings, vehicle details/orders/timetable, depot/purchase/refit/group views and town/industry details currently depend on desktop navigation. Use caller-selected references/context and explicit native tabs, sort, scroll and filters; preserve ordinary ownership rules and pixels-only perception. Avoid an arbitrary `WindowClass` renderer or a generic hidden-state report.
4. **Close finite presentation gaps.** Town directory filtering is genuinely absent; similar native search boxes are blocked by general input restrictions. Selected native filter fields or a narrowly reviewed presentation-only input allowlist can address those gaps. Do not assume keyboard/wheel/right-drag equivalents exist when only button and scrollbar paths are available. Verify actual row movement separately from changed PNG bytes.
5. **Make relevant rules inspectable without widening administrative input.** The settings route deliberately prepares a company-policy view and restricts tabs/rows. A separately reviewed read-only native presentation for gameplay rules could expose the chosen section while retaining mutation boundaries. Merely opening a settings window or returning a text query does not establish capture coverage of all rule pages.
6. **Preserve event context for transient views.** News, engine previews, buyout offers and script questions can be visible only when their native context exists. Any selected extension should capture an explicitly selected current/retained native context and report unavailability honestly, without fabricating events or choosing responses.

## Review and method

The native inventory and public capture surface were audited independently, then reconciled with an independent completeness review. The appendix was mechanically checked against the exact enum; source link targets and line bounds were checked. Operational and information-window callbacks were traced separately from class allowlisting. This document was written to the repository only after review of the combined draft. No implementation or test execution is part of this audit.
